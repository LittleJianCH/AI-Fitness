# Internationalization and Localization

**Read when:** adding user-visible text, changing error presentation, formatting measurements or dates, implementing language selection, or localizing Web/iOS/Android.

**Status:** implementation design; this document does not mean localization is implemented. Prepared on 2026-09-20 against AI Fitness [audited `main`](https://github.com/LittleJianCH/AI-Fitness/tree/712832d20ccf7d21538b406b87f8dbfda6bac14e) at `712832d20ccf7d21538b406b87f8dbfda6bac14e`. Recheck touched files before implementation. Apply [domain-data](domain-data.md), [API](api.md), and the relevant client guide where their boundaries are affected; do not load every guide.

## 1. Decisions and scope

Implement English (`en`) and Simplified Chinese (`zh-Hans`). English is the source/development language and final fallback; Chinese-speaking users should still get Chinese through language negotiation. This is an explicit initial product policy, not an inference that language determines location.

| Boundary | Decision |
| --- | --- |
| Web | Paraglide JS, maintained message files, generated typed message functions, and small client-owned formatting helpers. |
| iOS | Apple String Catalogs and native localization APIs. No third-party translation runtime. |
| Android | Android string/plural resources and Compose resource APIs when the client is initialized. |
| Haskell/API | Keep data, identifiers, validation codes, units, and timestamps language-neutral. No UI translation service or database migration for this slice. |
| Shared ownership | Share domain meanings and terminology; maintain platform-specific catalogs. Do not require identical keys or sentences across clients. |
| Preferences | Web-local language selection; native system/per-app language selection. No account-wide language synchronization initially. |
| Measurement units | Preserve current metric presentation and canonical units. Language selection never changes units. |

The goal is not to translate every string in the repository. It is to localize the existing product without changing authentication, imports/exports, calculations, data ownership, or user content. Repository documentation and operational logs remain English. Do not initialize Android, add an AI narrative service, or create translation infrastructure merely to complete this design.

## 2. Lessons from mature open-source implementations

These are inspected examples, not claims that every project uses the same library or that their entire architectures should be copied. Source snapshots and primary documentation are linked in section 11.

| Reference | Observed design | Adopt here / deliberately do not copy |
| --- | --- | --- |
| Immich Web | Its localization utility uses `svelte-i18n`, locale loaders, explicit Chinese script aliases, and language matching. Its translation guide describes ICU messages and Weblate. [I1], [I2] | Adopt explicit fallback/script handling, complete messages, and translator context. Immich is evidence for a production runtime-based alternative, **not** evidence that it uses Paraglide. Do not introduce Weblate or a large language registry for two languages. |
| Bitwarden iOS | Native `.strings` resources coexist with dedicated maintenance tooling for duplicate/unused entries and punctuation. [B1], [B2] | Adopt native resources and catalog hygiene. Do not copy its resource format or tooling wholesale: this project's Xcode baseline can use String Catalogs. |
| Bitwarden Android | Its Compose architecture example resolves labels through `stringResource`, and existing UI code does the same. [B3] | Adopt resource resolution at the UI boundary. Do not transplant its broader architecture or create a generic ViewModel hierarchy for localization. |
| Svelte CLI | Its Paraglide add-on provides project settings, Vite integration, hooks, and language/direction attributes. [S1] | Use an existing SvelteKit integration instead of a custom `t(string)` dictionary framework. Apply only the integration pieces our routing strategy needs. |

**Why Paraglide here:** the Web client has no existing localization runtime to preserve, already values typed generated interfaces, and uses SvelteKit. Paraglide fits those constraints. This is a project-specific choice, not a measured performance victory over `svelte-i18n`. Verify compatibility with the repository's pinned toolchain before migrating screens. Do not install both libraries. [S1], [P1]

Separate catalogs are also a project-specific choice, not a universal ban on shared translation sources. Native permission text, accessibility labels, and interaction wording differ. Revisit shared translation memory or standard catalog exchange only when actual duplicated translation work justifies it; do not create a cross-platform catalog compiler now.

The inspected source code, rather than older status summaries, establishes this baseline:

| Existing location | Relevant condition and intended change |

| `web/src/lib/workouts/presentation.ts` | Metric labels, missing-value messages, and `zh-CN` formatting are embedded in helpers. `groupCards()` uses the formatted day as its grouping key. Separate identities/grouping from rendered labels. |

This is a targeted inventory, not an exhaustive string count. The implementing agent must inventory additional affected files and keep each feature slice reviewable.

## 4. Preserve language-neutral data and errors

The dependency direction remains:

```text
Haskell canonical data / API codes
              |
     client state and adapters
              |
     client-owned presentation
              |
  translated text + formatted values
```

Never translate wire keys, sport discriminators, metric identifiers, field paths, revisions, cursor tokens, source identities, or exported canonical data. Existing English-looking identifiers are machine values, not English UI copy. Display localization must not alter import identity, calculation inputs, or persistence.

Usernames, workout titles, notes, tags, device names, and user-maintained equipment names are verbatim content. Localize the surrounding sentence or an application-owned default title, not the user's value. Do not write a translated default title back into a workout just because the language changed.

### Error presentation

Keep the existing `Problem` / field-error contract. Clients branch on stable `code` and, for field errors, known `path` plus `code`. Do not parse `message`, expose raw backend messages as normal UI, or make backend codes equal to frontend translation keys. Preserve unknown wire codes as data so a newer server does not make an older client fail decoding solely because a code is unfamiliar. [API contract](../api-contract.md)

A presentation mapping should distinguish known API failures, transport failures, cancellation, and unknown failures. An unknown server code must not automatically become a misleading network-error message. Show a localized generic failure and, where the existing response supplies it, a safe request identifier. Retaining a currently discarded `requestId` in a client error is a client change, not justification for a new API.

Use existing typed values such as `Retry-After` or advertised authentication policy limits for interpolated messages. Do not extract a limit from English diagnostic prose. If an important message truly lacks machine-readable parameters, use a truthful generic message first; propose a narrowly scoped contract extension separately rather than inventing a generic localization payload.

On Web, reuse `ApiError` and resolve text when rendering. On iOS, reuse existing error enums where possible; introduce a small semantic issue type only where a store currently loses meaning by retaining a translated string. Keep `FitnessCore` free of SwiftUI localization keys and app-bundle dependencies. Persisted state must not contain already-translated UI errors. Preserve retry, cancellation, and session lifecycle behavior.

This boundary does **not** prohibit all server localization. Future emails, notifications, or human-readable reports may need a server-side presentation renderer. Define that behavior when those features exist; do not localize the current canonical API in anticipation.

## 5. Language, formatting, timezone, and units

Treat these as separate inputs, not necessarily four new settings or classes:

```text
message locale   -> catalog selection, e.g. en or zh-Hans
format locale    -> regional date/number conventions, e.g. en-GB
presentation zone -> calendar dates and wall-clock display
unit preferences -> measurement conversion and unit labels
```

Native clients use their platform's language/region configuration. Web should retain an applicable regional preference for formatting rather than assuming `en` means `en-US`; when no applicable regional preference exists, use the selected message locale. Formatting helpers accept explicit locale/zone inputs so this behavior is testable. Do not invent an account settings API for these inputs.

### Web language policy

Resolve an explicit, validated language cookie first, then supported browser/request preferences, then `en`. “System” means no explicit override: clear the override rather than persisting today's detected language forever. `system` is a preference mode, not a translation language tag.

Use BCP 47 tags and a small, tested normalization boundary. Honor preference order and HTTP quality weights; malformed values and `q=0` entries must not win. Use library matching where it meets the policy, adding only a narrow adapter if required. Do not assume a strategy name proves script/region matching is correct. [P2]

Required Web examples:

| Input | Message locale |
| --- | --- |
| Explicit `en`, browser prefers Chinese | `en` |
| `en-GB` or `en-US` | `en`, with applicable regional formatting retained |
| `zh-Hans`, `zh-CN`, or `zh-SG` | `zh-Hans` |
| `zh-Hant`, `zh-TW`, `zh-HK`, or `zh-MO` | Try the next supported preference, otherwise `en`; do not silently label Simplified Chinese as Traditional Chinese. |
| No supported preference / invalid override | Negotiated supported language, otherwise `en` |

An explicit script takes precedence over region-based aliases. Native clients should declare the actual supported localizations and use platform resolution; test their script fallback on the supported OS versions rather than replacing native resolution with the Web matcher. Never add application aliases that claim `zh-Hant` content exists when it does not.

Keep `/workouts` and other application URLs language-neutral. No locale-prefixed routes, translated paths, or SEO routing work in this slice. The non-secret language cookie is independent of authentication; scope it to the application, use appropriate SameSite/Secure settings, and never let it influence authorization.

### Formatting and grouping

Provide a small formatting boundary per client using native facilities: Web `Intl`, Foundation format styles on iOS, and Android/JVM locale-aware formatters. Do not replace these with hand-maintained month names or a universal formatter DSL. Centralize locale-sensitive policies, not every string operation. Language literals are legitimate in catalogs, locale configuration, and tests; they should not be scattered through feature formatters.

A workout's calendar-day grouping key must come from its instant **and chosen presentation timezone**, using a defined Gregorian `YYYY-MM-DD` representation. Translate the heading separately. Do not use a formatted label as identity, and do not substitute `toISOString().slice(0, 10)` when local-day grouping is intended. Switching language with the same zone must preserve group membership; switching zone may legitimately change it.

Preserve existing timezone behavior. This task does not introduce an activity-local/account timezone policy. If the browser's zone is unavailable during SSR, do not silently use the server's zone for personal dates: render a deterministic placeholder or defer those values until the client zone is known. Keep SSR and hydration consistent.

Durations are elapsed quantities, not calendar instants. Preserve the existing duration precision and distinguish it from clock time. Keep zero distinct from absent measurements. Measurement formatting must apply conversion consistently to values, axes, tooltips, and summaries; do not change only a unit label. Imperial support is outside this slice.

Display formatting is not input parsing. Preserve the existing validated numeric/date input contract; never parse localized text by blindly deleting commas, and never change canonical decimal/UTC serialization with the UI language. A future change to accepted localized input syntax needs explicit tests and product behavior.

## 6. Messages and translator context

Use complete messages with named or platform-supported typed placeholders, not concatenated sentence fragments. Let the selected message system handle plural/select variants. English count-dependent messages need the relevant singular/plural forms; Simplified Chinese should use its applicable forms, not artificial English grammar. The same numeric argument must drive plural selection and displayed count. Paraglide variants are not interchangeable with arbitrary ICU syntax; use its supported format rather than pasting an ICU message and assuming it works. [I2], [P3], [A1], [D2]

Web keys should be stable semantic names such as `auth_invalid_credentials`, `workout_delete_confirmation`, or `metric_heart_rate`. Do not construct arbitrary translation keys from untrusted API strings. Use explicit typed mappings with an unknown-value fallback. Share a key only when meaning and context match, not merely because two English words happen to match.

On iOS, extractable English literals in localization-aware APIs are valid source messages. Do not ban `Text("Retry")` or replace every literal with an untyped lookup wrapper. For ambiguous meanings or reusable messages, explicit keys/default values and comments are appropriate. Android uses semantic resource names. Cross-platform spelling of keys is not a public contract.

For ambiguous or parameterized messages, record purpose, screen/action context, placeholder meaning/unit, and relevant restrictions using supported catalog metadata, Swift localization comments, or XML comments. Do not put fake comment keys into runtime JSON catalogs. Keep fixed product/protocol names such as `AI Fitness` and `FIT` unchanged unless an actual branding policy says otherwise.

Initial terminology guide; this is translation guidance, not a replacement for the API schema:

| Concept | English | Simplified Chinese | Meaning to preserve |
| --- | --- | --- | --- |
| One recorded workout | Workout | 运动记录 | Not an authentication session or future training plan. |
| Cycling / running | Cycling / Running | 骑行 / 跑步 | Display labels for stable sport values. |
| Power / heart rate | Power / Heart rate | 功率 / 心率 | Preserve the metric and measurement unit. |
| Cycling / running cadence | Cycling cadence / Running cadence | 踏频 / 步频 | Distinct meanings despite the shared English word. |
| Moving / timer / elapsed time | Moving / Timer / Elapsed time | 移动时长 / 计时时长 / 经过时长 | Never collapse the three measurements into one label. |
| Recorded / calculated statistic | Recorded / Calculated | 记录值 / 计算结果 | Preserve device/manual provenance; neither means “more accurate” automatically. |
| Missing value | Not recorded | 未记录 | Not zero and not necessarily a computation failure. |

All user-visible surfaces count: form validation, empty/loading/error states, toast/dialog text, chart accessibility, tooltips, navigation labels, page titles, screen-reader descriptions, and application-owned permission explanations. Symbols like `W` need not have redundant translations, but their spoken descriptions may need localization.

Treat translated markup and interpolated user values as untrusted text. Prefer escaped text/structured rich-text APIs; no `{@html}` or equivalent raw HTML injection for translation convenience. Do not interpolate user content into a message key.

## 7. Web implementation

Proposed maintained locations, not existing files:

```text
web/messages/en.json
web/messages/zh-Hans.json
web/project.inlang/settings.json
web/src/lib/i18n/format.ts
web/src/lib/i18n/errors.ts
web/src/lib/paraglide/             # generated, ignored
```

Start with one catalog per language and semantic prefixes. Split catalogs only when review/ownership or tooling benefits are demonstrated. Formatting and error modules should remain direct functions; no service container or vendor-neutral translation framework.

Integrate Paraglide into the existing Vite/check/build flow and SvelteKit hooks. Preserve existing hooks, routing, session boundaries, base paths, demo mode, and connected mode. Disable URL-based localization for this policy; do not blindly keep every generated demo or reroute hook from the CLI. [S1], [P1]

Server rendering must use request-scoped locale state. Do not mutate a process-global locale per incoming request or disable request isolation to silence an integration error. Initialize the client from the server-resolved language before hydration; independently consulting browser preferences during the first client render can produce a different result. Set document `lang` and `dir` from the same resolved message locale. Do not publicly cache personalized localized HTML; retain existing private/no-store behavior. [P1], [P4]

Use generated message functions directly in views or small typed presentation mappings. Do not evaluate localized strings once at module import time. Raw API query keys stay language-neutral because their payloads have not changed; locally derived display models and ECharts options must be refreshed when their presentation inputs change. Keep series identifiers and chart calculations independent of translated names.

A full reload on language change is acceptable for the first implementation and matches Paraglide's default switching behavior. Reuse the existing unsaved-change protection **before** committing an override or reloading; canceling the switch must retain both the draft and prior language. Do not add reactive locale infrastructure solely to avoid a safe reload. Background operations must not be duplicated by a language change. [P1]

Pin the compiler and message-format plugin inputs using the repository's package/lock conventions; avoid floating `@latest` or moving remote plugin URLs in reproducible builds. Generation must run before checks/tests/builds that import generated messages, including clean-checkout workflows. Do not assume the Vite dev server has already generated them. Add commands only when implemented, then document them in `web/README.md`. [P5]

## 8. Native implementation

### iOS

Add `Localizable.xcstrings` and `InfoPlist.xcstrings` to the app target under `ios/App/`. Configure development language, supported localizations, target membership, and Swift string extraction in the actual Xcode project. Localize the HealthKit usage descriptions and other existing app-owned privacy prompts without changing what permissions are requested. Do not introduce newer Xcode-only generated-symbol syntax or raise deployment targets just for localization. [A1]

For custom presentation components, prefer `LocalizedStringResource` where passing localizable content with context/defaults; `LocalizedStringKey` remains appropriate for SwiftUI-only APIs. Provide a clear verbatim path for usernames and other dynamic content, or accept composed `Text` at that boundary. Do not blindly convert every `String` property to a localization key. Resolve messages using the active view locale; a long-lived localized resource or preformatted string must not freeze the wrong locale in tests or future in-app switching. [A1]

Move application-owned display explanations out of core state where necessary, retaining structured data/issues. Keep catalogs in the app while `FitnessCore` has no real resource ownership need. If a future package genuinely owns localized resources, declare its default localization/resources and use the correct package bundle instead of assuming `Bundle.main`. No duplicate app/package catalogs for the same ownership boundary.

Use system/per-app language selection initially; do not add a custom bundle-swizzling mechanism or mutate `AppleLanguages` to force localization. Verify actual language/region launches and the custom-component boundary. Keep accessibility identifiers stable while localizing their human-facing labels.

### Android, when initialized

Use complete English defaults in `res/values/strings.xml` and Simplified Chinese in `res/values-b+zh+Hans/strings.xml`. A separate identical `values-en` file is unnecessary. Use `stringResource` and `pluralStringResource`, with matching typed/positional arguments; keep composables responsive to configuration changes. Domain/data layers must not require an Android `Context` just to carry an error. [B3], [D1], [D2]

Expose the actual supported languages through the platform's per-app language configuration. Choose manual or build-generated locale configuration according to the selected Gradle/SDK baseline, not both. Do not accidentally advertise dependency languages that the product has not translated. An in-app picker, if added later, must use the platform/AndroidX locale APIs rather than a separate conflicting preference system. SDK/backward-compatibility choices remain part of Android initialization, not this document-only task. [D3]

## 9. Catalog ownership, workflow, and safeguards

Commit maintained message catalogs, `.xcstrings`, Android XML resources, translator context, required build configuration, and dependency locks. Ignore generated Paraglide functions/declarations, compiled native resources, build outputs, and temporary localization exports. A catalog automatically updated by Xcode still contains maintained translations and **must be versioned**. [A1]

Keep source/translation edits together for the small initial language set. Missing required translations should fail release acceptance, even though runtime fallback remains necessary for resilience. Review stale/unused entries before deletion; dynamic/native extraction limitations make blind regex deletion unsafe. Use the platform's native extraction and diagnostics first, adding only small targeted checks for uncovered requirements. [B2]

No translation server, translation database, custom universal message AST, automatic online translation at runtime, or bulk AI translation of user records. Translation-management services can be considered when contributors need them. If an external translator or AI is used later, send only application-owned copy and synthetic context—not health records, routes, credentials, screenshots containing personal data, or real server error payloads. Adding a translation provider requires its own authorization/data policy.

Future generated analysis is a separate feature: retain language-neutral calculation inputs/results, and attach the requested output language to any persisted narrative. Language-specific narrative caches must include language and relevant input/version identity. Do not add those APIs, models, or caches in this migration.

## 10. Implementation slices and acceptance

These are handoff slices, not a requirement to create every proposed file at once. Keep the application runnable after each slice and do not mix business refactors with translation extraction.

| Slice | Work and completion boundary |
| --- | --- |
| 1. Web foundation + one journey | Add locked generation/configuration, locale resolution, and localized shell/login or another complete existing journey. Demonstrate clean-checkout build, both languages, fallback, SSR isolation, and safe switching. |
| 2. Workout presentation | Migrate measurement/date helpers and stable day grouping; cover list/detail, charts, missing values, and accessibility while preserving data and timezone semantics. |
| 3. Remaining existing Web surfaces | Migrate forms, account/session UI, FIT import states, dialogs, validation, and error mappings. Update tests and complete both catalogs. |
| 4. iOS | Wire native catalogs, localize app-owned permission text, fix component/issue boundaries, and validate login, workouts, and explicit HealthKit import/export flows. |
| 5. Android | Apply native resources as part of the separately authorized client initialization. Its absence does not block completing the current Web/iOS migration. |

Required regression cases:

| Area | Acceptance |
| --- | --- |
| Catalog integrity | Referenced keys exist; active messages are translated in both locales; placeholders/types and required plural branches agree. A deliberately missing translation is detected by checks and has a safe runtime fallback. |
| Language resolution | Cover overrides, system reset, unsupported/invalid tags, ordered preferences, quality weights, Chinese script aliases, and regional English. Document native fallback behavior separately. |
| Concurrent SSR | Interleave English and Chinese requests and verify no locale leakage, incorrect `lang`, or first-render hydration language mismatch. |
| Date identity | With a fixed zone, changing language does not change day groups or keyed UI identity. Test near UTC midnight and local DST transitions; presentation and grouping use the same zone. |
| Measurements | Zero differs from missing; unit symbols, precision, durations, chart values, and recorded/calculated provenance remain correct. |
| Error handling | Known/unknown API codes, field issues, network failure, and cancellation behave correctly. Unknown errors never dump raw server diagnostics or impersonate a specific known failure. |
| Unsaved work and lifecycle | Switching or canceling a language change preserves the documented dirty-form behavior; no duplicate submission, import, export, or authentication transition. |
| User content | A workout title or username that equals a translation key remains verbatim. Mixed-language notes and escaped markup remain unchanged. |
| Layout and accessibility | Exercise both languages at desktop and narrow mobile widths, large text, long synthetic strings, and platform pseudolocales where available. Localize accessible names without changing stable test IDs. RTL probes must not mirror chart time axes or imply a shipped RTL translation. |
| Build/resource ownership | A clean checkout generates Web imports before checks; native catalogs are present in the correct bundle; no generated artifacts enter Git. |
| Data invariance | For fixed input and export context, language changes do not alter canonical values, revisions, IDs, authorization, or the documented export projection. Do not compare exports with intentionally different timestamps as if they should be byte-identical. |

Prefer unit tests for mapping/formatting and a few end-to-end journeys in each supported language. Keep role/accessibility-based tests meaningful; use stable IDs for language-independent actions and explicit localized-label assertions for translation behavior. Do not convert all tests to opaque selectors.

Use existing configured checks from the affected client README/manifests; add localization-specific checks as part of implementation. Run Xcode app builds/UI tests for catalog membership and permission copy—`swift test` on the core package alone cannot establish that. Report unrun device/platform checks honestly. A documentation-only change does not establish that any runtime acceptance case has passed.
